# CLAUDE.md

## Project Overview

inksprite is a writing application with AI integration. It runs entirely in the browser: no backend, data in IndexedDB, AI requests straight from the client to the provider.

Features:
- **Editor**: Distraction-free editor (ProseMirror) with markdown support, a bar under a selection (comment, link, bold, italic, the other marks and Clear formatting in a menu, and the style: normal text, headings, code block, quote, lists; on a phone at the bottom of the screen), find and replace on Command-F, a search across the project on Shift-Command-F (a list in the sidebar, by document, each match opening its document at it with the find on it; a PDF at its page), spelling and grammar checked by Harper in a worker (English; the project's names known; no autocorrect), pictures (pasted, dropped, inserted, or kept from an imported Doc or Word file; each its document's own, at `.images/<document id>/` beside it, with alt text, never fetched from the web), formulas (TeX between dollars, typeset by KaTeX where it stands and opened as written to be changed, typed or put in from Insert › Formula and Shift-Command-E), and focus mode on Option-Command-F: the document alone, full screen
- **Projects**: A project is a tree of documents. Folders hold children; text documents hold content; file documents are imported files (PDFs, images, anything) whose extracted text is their content and whose bytes live in the `files` table (a file of text over 50 MB, a data set more than anything to read, keeps its bytes alone, and a file over 1 GB isn't taken). A folder can be ordered, in which case its children sort by position and can be dragged into place; otherwise they sort by title. A document can hold others as a folder does, where the app brings in both: a Scrivener text its children, an epub its chapters, a card that came in a picture its fields, a PDF the Markdown converted from it; only the imports and Convert make one, and of those only a card takes new documents, made, dragged or imported into it, as a folder does (`takesDocuments`); what the others hold is renamed in place or moved out. A new project starts empty; the writer lays it out. The app opens on the project the writer was last in, and with none to open, on an Untitled project that is saved only once something is done in it (a document, a chat, a new name, its settings), as a chat not started is, and let go of if left untouched. The outline's hamburger lists the recently edited under Recent projects (opening on hover), and Projects… is every project in a table, searched by name and sorted by name, last edited or created, with whose each is and who else is in it once any is shared, and the invitations waiting at its top; a right-click on a project in either gives it the outline's project menu, without opening it. The open project's title, summary, default chat profile and sharing are its own section of the settings, Settings › Project; in the desktop app, Show in Finder on the outline's menus opens a project's or a folder's directory and shows a document's file. A Scrivener 3 project can be imported, as a new project or into a folder: the binder as the tree, each text as markdown. The desktop app opens more windows from File › New Window, a project in one at a time; its windows and a browser's tabs tell each other what they change (`platform/windows.js`), though two tabs on one project still write over each other. (The storage still calls a project a story: the `stories` table, `storyId`, and the `Story` typedef.)
- **AI Integration**: OpenRouter and NanoGPT (each with a sign-in), llama.cpp, and any OpenAI-compatible endpoint. A model's settings are kept per connection and model (a preset, made the first time one is changed and holding only the changes, over the samplers OpenRouter lists for the model), and edited in its card in Settings › Models, behind the card's sliders button (an OpenRouter model's Providers among them, and a NanoGPT model's where NanoGPT lets them be chosen). Settings › Models is the model picker: the few models that answered lately (`modelUses`, kept on the device), the recommended ones, then each connection's, sorted by name or cost, a group shut by a click on its heading; with a chat showing, a click puts the chat on the model. A chat keeps the model it first answered on, its reasoning effort and whether its edits wait, chosen from the chips under its message box (the model chip: its model, those chosen lately, its effort, and Other models…, which opens Settings › Models); a pick there also starts the profile's next chats on it, and no chat already going moves, nor does changing or deleting a preset move one. There is no app-wide default: a profile never picked on starts its chats on the built-in preset (`useProfiles`), and Convert keeps its own model, chosen in its dialog (`.llm/ai_setup_design.md`). The connections are the writer's, none made on start: the chat's "No AI provider is connected" opens setup (connect a provider, checked for real, then choose a model, one suggested), and Settings › Connections › AI providers lists them, a card saying only what went wrong when it last answered (`useConnections`). An OpenRouter connection carries its provider routing, and a NanoGPT one zero data retention, on by default. A failed reply offers what fixes it: the connection's settings, credits, or another model. Each connection takes so many requests at once (Requests at once; one for a server at home, or llama.cpp's slots, and no limit for a hosted service, which is asked less at once when it answers 429), and what the writer is waiting on goes before a job's. The AI can be switched off in Settings › System (and from the welcome): the chat, the narration, the AI's settings sections (Settings › AI among them) and its outline marks and menu items go, and what they hold is kept for when it is back on.
- **Chat**: Brainstorm with the AI, which reads, searches, creates, and writes the project's documents through tools, and searches the web and reads pages through the Web search extension (Exa or Kagi, and Brave in the desktop app; its key in Settings › Connections › Web search, where a card's Use for web search makes it the one used, as Search with in Settings › Extensions does; on in a chat as any tool is). It keeps a page or a document it found (a PDF as the file itself where it can be fetched, which in a browser it mostly can't) in the project, asking first until the writer says Always allow. A document is attached to a message with `@` in the message box: its text is copied onto the message as it is sent, goes to the model ahead of what was said on every later turn, and counts as a read (`ai/context/attachments.js`); `[[` there links a document, or a folder, for the model to read if it wants. Conversations can be compacted into a summary of themselves, asked of the chat's own model at the end of the conversation, so it is written from what the model has: the documents read and attached among it (`askInThread`). Math written in TeX is typeset (KaTeX, loaded the first time a formula needs it). Command-F finds in the whole chat, though only the turns near the screen are in the page. Chats open in tabs above the chat, as documents above the editor (`useChatTabs`): one picked from the list is a preview until sent in, New chat, a fork and `/fork` (a copy of the whole chat, its message sent there; it took `/aside`'s place) open beside the tab showing, closing goes back to the tab shown before, and a chat the model is working in has a spinner, one it stopped in unseen a dot, on its tab and in the list. Under a chat's message box are chips: its profile, its model and effort, and Suggesting or Editing (whether its edits wait). Settings, with a chat showing, carries the chat's profile atop its list and the chat's own sections among the rest: Prompts (Roleplay under them in a roleplay chat), Models, Tools and Skills. A right click on a turn's Read aloud sets the voice its side is read in. A chat that asks before changing documents suggests its edits to a text document in the text, each change accepted or rejected on its own in the Comments tab (a plain document's, a new document and a delete are proposed in the chat). What the model appends to a document open in the editor shows at its end as it is written, and goes in when the call runs (`editor/streaming.js`). `explore_documents` and the writer's `/explore` write a line on what each document, folder and long section is about, which the listings show the model; the chat asks before exploring a lot.
- **Profiles**: A chat runs under a profile: its system prompt, which tools it is offered, the author's note it starts with, its wording of each built-in skill, and the model its chats start on (the last picked in a chat on it). The profile chip, under the message box and atop Settings, is a menu (`ProfileMenu`): it picks another, stars the one new chats start on where a project hasn't chosen, makes one under a name from the chat's settings (New profile…), opens its prompts (Prompts…), and on a right click sets the default, and renames or deletes one of the writer's own. Settings › Prompts has a Save beside the prompt and the note, and Settings › Skills words a built-in skill for the profile showing (the model and tools go to the profile as they are picked); a built-in is saved to in place (`system.builtInProfiles`). A skill of the writer's own is a card of three fields there, Name, Description and Instructions, kept when its check is clicked (the name written as a title, its command made from it), and its whole SKILL.md opens in a tab of the editor for the rest; one that can't be used says why under its instructions, and is offered to nobody (`.llm/skills_rework_design.md`). Tools are one list in Settings › Tools, by where each comes from (the documents, the web, Python, each MCP server, skills, RPG), and switched one way (`ai/tools/choice.js`): a switch in a chat goes to its profile too, Enable tools greys the list without changing a switch, and something added (a server, a search service, Python) is on wherever nothing switched it off, but on Blank and Roleplay, which offer only the groups they name; the Settings pages only add, and a tool that asks first is marked so in the list. The built-ins are Default (the project and its tools), Roleplay and Roleplay (NSFW) (a scene, with the document tools and no others; a card's chat opens with a turn of the writer's that attaches the card's documents, ahead of its greeting, and a summary leaves the first two messages of a roleplay chat standing; the NSFW one carries the opt-ins the writer lists in its author's note, and takes Roleplay's place while Settings › Extensions › Roleplay › Enable NSFW chat profiles is on: chats on Roleplay, card chats among them, run on it then, and chats on it run as Roleplay while the switch is off), and Blank (no system prompt, no tools, no project). The RPG tools (dice, oracle, tables, tarot, names) are offered in chats that have them on; the Adventure prompt they were tuned under lives in `app/harness/prompts/` for the harness. Interpret and Write, skills still being tuned, are the harness's (`app/harness/skills/`), set beside the built-ins while it runs, and not in the app.
- **Extensions**: Parts of the app not every writer wants, each switched on in Settings › Extensions (there while the AI is on). The first is **Roleplay**: character cards (Files… reads them as cards, Import › Character card…, Chat with…, Re-import card…), the card library, the Roleplay profiles in the pickers, and its own settings (Enable NSFW chat profiles, Profile for character cards, Delete card library). Off, all of that is hidden and nothing is deleted: card folders stay, chats on a Roleplay profile keep running on it, and the card library is kept. Decided once at upgrade: on where roleplay was in use (library cards, NSFW on, a card profile chosen, a chat on Roleplay or naming a character), off otherwise; new installs start off. The RPG tools are not part of it. **Web search** is on from the start: the service searched with and Ask before saving pages; off, the Web tools are offered to no chat and Connections lists no search services. **Python** (the desktop app only) is the model's `run_python`, the standard library, numpy, pandas, pyarrow and duckdb in Pyodide, fenced from the app's data and the network, the chat's project read-only at `/project` (a file's text beside it, a PDF's among them, and a file still on the sync server fetched as it is read), a session for each chat, in every chat that has it on among its tools (all but Blank's and Roleplay's to start); a script it keeps in the project (a `.py` document, kept as written) it runs by its path.
- **Card library**: The writer's character cards, kept as cards outside any project: a grid of portraits to search by name, creator or tag (typing a tag's start offers `tag:` filters; the sort chosen is kept), each card shown in full, a split button that starts a New project named for the card (its card on the shelf, then straight into the Chat with questions and the chat), opens the project made for it once there is one, or adds it to the open project; the card remembers the projects it went into and its detail lists them (a folder's Import › Character card… imports into that folder); a card's right-click menu and its detail also download it (its PNG, or its JSON) or delete it. Cards tagged nsfw or nsfl show blurred pictures until the eye beside the search turns blurring off (on by default, kept). Cards also come from a link (the link button, or a link dropped on the library): a botbooru or Chub page, Chub's creator/name, or the card's own address, fetched through platform/fetch (botbooru only works in the desktop app: no CORS). Its rail button sits under Chats while Roleplay is on.
- **Trash**: Deleted documents, folders, chats and projects go to the trash without asking, kept 30 days and restorable from Projects › Trash (the outline header's hamburger, while anything is in it); Command-Z in the outline takes a delete back. The model's `delete_document` deletes to it too.
- **Versions**: A text document keeps versions of itself, taken after a pause in typing and before a change from outside the editor (the model, a sync, a re-imported card), thinned with age; Versions… on its menu or its tab compares one with the text and restores it.
- **Sync**: The writer's projects, setup and card library on all their devices, through a server of ours at `sync.inksprite.io` that holds them encrypted (Settings › Sync and sharing). An account is made with an invitation's code, under a name of a–z, digits and hyphens, with a passphrase and a recovery code; a project can be kept on one device only, or shared with friends by their friend codes from Settings › Project (its menu's Share…), whole or only the documents ticked (in the `selective-sharing` preview: unshared ones are the owner's own, a new one follows its folder), as an invitation each friend accepts, rejects or answers with a block (a toast on their devices, and a greyed row in Projects…; a block ends every share between the two, both ways): everyone can write in it, only its owner shares it, and each one's chats in it are their own. Removing a shared project puts it in that account's trash alone, out of sync until restored; after 30 days a friend leaves it, and its owner hands it to the friend who joined first. People are known by their account names; Settings › Sync and sharing is Account (the friend code first, and what sync is doing), People (kept by the server, offered by name in Share…, those blocked shown on asking), Devices and Backup, each a part of the section, listed under it while it is open, as Connections' AI providers, MCP servers and Web search are.
- **Export**: A project, a folder or a document handed out as it would be published, to be used elsewhere (Export project, and Export on every folder's and document's menu; `files/exportDocument.js`): files and directories by the outline's paths, each text as it stands without comments or suggestions, each imported file as it came in, a text's pictures in an `images/` folder beside it, and every link to a document in the export written to the name the export gave it. One file goes as itself and more as a zip; in the desktop app a project or a folder goes to a folder the writer chooses, one there of that name going to the system's trash first. A text document also goes as a PDF, in the editor's styles (Export as PDF… on its menus, which in a browser is the print dialog; Command-P prints the one open; `composables/usePrint.js`). Nothing of it is read back in.
- **Backup**: Export (Settings › Sync and sharing › Backup) is everything, the projects with their chats, trash and versions, the card library and the settings, with a switch for API keys; taken back, it replaces everything or adds the projects and cards ticked beside what is there. Export settings beside it makes a settings file of the settings ticked. A backup is a zip (`utils/backupArchive.js`): its rows as JSON, a table in one entry or several, and each file's bytes as an entry of its own, so none of it has to fit in one string (a browser's are about 512 MB at most); a settings file and a chat are still JSON, and the JSON backups, project files and selections from before still import. Old backups are moved forward by migrations.

## Development Commands

These commands are run from the `app/` directory.

- **Install dependencies**: `npm install`
- **Run development server**: `npm run dev`
- **Build for production**: `npm run build`
- **Preview production build**: `npm run preview`
- **Lint code**: `npm run lint`
- **Fix lint issues**: `npm run lint:fix`
- **Format code**: `npm run format`
- **Check formatting**: `npm run format:check`
- **Generate docs**: `npm run docs` (done when a snapshot is published, not with each change)
- **Type check**: `npm run typecheck`
- **CI**: `npm run ci`
- **Fix CI issues**: `npm run ci:fix`

## Test Server

There is a test server container running with `docker compose` that is hot updated by Vite. After a change to the app's dependencies, or a merge that touches `package.json`, `package-lock.json`, `vite.config.js` or `index.html`, the user rebuilds it with `./rebuild-test-server.sh` from the repository root, on their Mac. Never `npm install` inside the container: those files are mounted one at a time and go stale when git replaces them.

The desktop app (`app/electron/`) runs on the user's Mac with `app/electron/start-on-mac.sh`, loading the page from the test server; see `app/electron/README.md`. npm never runs on the Mac: `npm ci` in `app/electron` happens in the container, and the script fetches the Mac's Electron itself. `app/electron/install-on-mac.sh` on the Mac builds dev's app in the container (`build-for-mac.sh`, through docker), signs it and puts it in place of the installed app. The user runs it when they want dev in the desktop app, so nothing is built after a merge.

## Development Cycle

A change goes into dev as soon as it works and looks right, and is finished once its design stops changing. The user tries it on dev and asks for changes there, so tests of its UI and its docs written before then would be rewritten with every round.

1. **Build** in a worktree, `.claude/worktrees/<name>` branched from dev, with the main checkout's `app/node_modules` and `app/harness/test-*` folders linked into it (so the card tests run there too).
   - As you go, run `npm run lint`, `npm run typecheck` and `npx vitest run --changed dev` (the tests of what the branch changed), not the whole suite.
   - Before handing it over, look at it in the browser with Playwright, on a dev server of the worktree's own (`npm ci` there rather than the link): the user reviews it working, not half done.
   - Logic gets its tests as it is written: stores, composables, utils, the AI, storage, sync. A test of logic the change breaks is fixed.
   - Components don't, yet. A component test the change breaks because it pinned the old UI is deleted, not rewritten, and the component's tests are owed.
   - No docs yet: no guide pages, feature text in CLAUDE.md, "as built" in the design doc, module docs or capture scripts. What the change owes goes in `.llm/owed/<name>.md`, a line each.
2. **Ask to merge.** First merge dev into the branch and run `npm run ci` once, there. The merge into dev then makes the tree CI just passed, so CI runs again only if dev moved in between.
3. **The user tries it** on :8002, or in the desktop app with `install-on-mac.sh`. What they ask for goes through 1 and 2 again.
4. **Finish** once the user stops changing it, or before the next snapshot is published at the latest: component tests of the UI it ended with, the guide pages, CLAUDE.md, the design doc's "as built", the capture scripts. Then delete `.llm/owed/<name>.md`; nothing is published while `.llm/owed/` holds anything.

## Guidelines

### Clean Code

- Write clean, idiomatic code
- After implementing a complex feature, review your work and refactor if necessary
- If a change doesn't fit well with the current architecture, refactor or redesign rather than adding technical debt
- Create a commit after each significant change
- This project uses JSDoc for type checking. Ensure that types are respected and documented correctly.
- Use `npm run ci` to run the linter, format checker, type checker, and tests.
- Use `npm run ci:fix`  to fix lint and format errors.

### Help text

Most controls need none. A note under a setting, or in a dialog, says only what the control can't say for itself: its scope ("Applies to every chat"), a format, or a warning ("Edits made since are lost"). Keep that to a line. Never restate the label, and never explain how the app works inside; a result the app reports afterwards (a toast, a status line) needs no note ahead of it. No Enabled/Disabled tooltips on switches. Commit 50a8bbfe, which cut the app's help text down this way, is the model.

### Messages

Most actions need no message: the writer sees what happened. A toast is for a result they can't otherwise see (connecting to a provider, a copy to the clipboard), a loss ("This can't be undone."), or an error they have to act on, in plain sentences: what didn't happen, then why ("The provider couldn't be reached." and the reason). An action that can't apply does nothing. A conflict is settled without asking, as sync settles one: one side wins and the other is kept as a version. A confirm guards only what can't be taken back; what goes to the trash, or that Command-Z undoes, goes ahead. Developer strings (ids, "Failed to …") go to the console, never to the writer.

### Lists of things

A list of things to pick or open, in the settings or a chat's, is a `CardList` of `CardItem`s (`components/common/`), headed by `CardHeading`s where it has groups, as the model list is: a name, a line under it, a few words on the right, the one in use tinted, and the one open with what it holds below it.

### Preview features

A large feature the user wants to use for a while before it is released is merged into dev as it is built, behind a preview, rather than kept on a branch:

- Add it to `PREVIEWS` in `app/src/config/preview.js` with the day it went in, and check `inPreview('<name>')` wherever it reaches the writer or the model: menu items, commands, tools, settings, skills.
- Never put what it stores behind it. Its fields and migrations ship in every build, and only add, so a backup or a library written with the feature opens in a build without it.
- `VITE_PREVIEW` in `app/.env.local` (names, or `all`) turns previews on for the test server and the Mac dev build. The test server reads it when the container is made, so a change needs `./rebuild-test-server.sh`. The site and the released desktop app are built without that file, the guides' capture clears it, and the tests never read it, so a test of a feature in preview turns it on with `vi.stubEnv`.
- Out of preview, remove its checks and its `PREVIEWS` line, and put it in the next CHANGELOG section.

### Sync format

A synced record carries its schema and its format (`app/src/cloud/format.js`), and an app that meets a newer one holds its pull until it is updated. Raise `FORMAT` when a synced row may come to hold what an older app would lose or rewrite as it saves: the editor learning a node, a mark or an attribute (`test/cloud/format.test.js` pins them to the number), new markup in a document's text, or a field coming to mean something else. A raise holds every device not yet updated, so avoid one where an older app can carry the change through unharmed, and more so once the app is stable.

### Dev features

What is only for developing inksprite, and never released, checks `hasDevFeatures()` (`app/src/config/dev.js`), which `VITE_DEV_FEATURES=true` in `app/.env.local` turns on, read as `VITE_PREVIEW` is. So far: choosing the sync server, which is otherwise `sync.inksprite.io`.

### Third-party material

This repository is published. The rulebooks, books, papers, character cards and chats we test against are other people's work:

- Keep them in the gitignored folders: `app/harness/test-*/` (cards, chats, PDFs, epubs), `app/harness/research/`, and `local/` at the repository root.
- Never name them in anything committed: design notes, comments, tests, fixtures, harness findings, commit messages. Describe them by their role instead: "the largest rulebook", "a third-party card", "a novel".
- Never copy their text into a test or fixture, not even a heading or a line. Make up text of the same shape.

### Testing

The project uses **Vitest** for unit and integration testing, with **@vue/test-utils** for Vue component testing.

#### Test Commands

Run these commands from the `app/` directory:

- **Run all tests**: `npm test`
- **Run tests in watch mode**: `npm run test:watch`
- **Run tests with UI**: `npm run test:ui`
- **Generate coverage report**: `npm run test:coverage`

#### Test Structure

- Tests are located in the `app/test/` directory
- Test files follow the naming convention: `*.test.js`
- Tests are organized to mirror the source structure:
  - `test/stores/` - Pinia store tests
  - `test/components/` - Vue component tests
  - `test/utils/` - Utility function tests
  - `test/composables/` - Composable tests

#### Writing Tests

##### Store Testing
- Mock the database layer and external dependencies
- Test state management, actions, and getters
- Ensure proper initialization and error handling
- Example: `test/stores/storiesStore.test.js`

##### Component Testing
- Use `@vue/test-utils` for mounting components
- Mock router, stores, and external dependencies
- Test user interactions, props, and emitted events
- Test both rendering and behavior
- Example: `test/components/BookCard.test.js`

##### Utility Testing
- Test pure functions with various inputs
- Cover edge cases (null, undefined, empty values)
- Test with different data types and formats
- Example: `test/utils/wordCount.test.js`

#### Best Practices

1. **Isolation**: Each test should be independent and not rely on other tests
2. **Mocking**: Mock external dependencies (database, API calls, stores)
3. **Coverage**: Aim for high code coverage but prioritize meaningful tests
4. **Descriptive Names**: Use clear, descriptive test names that explain what is being tested
5. **Setup/Teardown**: Use `beforeEach` and `afterEach` for consistent test state
6. **Assertions**: Make specific assertions that test one thing at a time

### Documentation

Project documentation can be found in `app/docs/index.md`. High level documentation for a module can be found in the associated `index.js`, e.g. `app/src/stores/index.js`.

- Add JSDoc comments to all functions for type checking and documentation
- Update module documentation as needed, when the change is finished (see Development Cycle)
  - New modules should be created with an `index.md`, similar to `app/src/stores/index.js`
  - Update the `index.js` file for a given module when required
  - Update the project level `app/docs/index.md` if the structure of the project changes
- Leave the generated module docs (`app/docs/*.md` other than `index.md`) alone: they are regenerated with `npm run docs` when a snapshot is published. The generator orders some modules differently from run to run, and branches that regenerated them as they went conflicted on merge.
